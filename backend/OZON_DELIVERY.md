# Бесплатные пробники и Ozon Доставка

Страница `/prob` показывает товары из Google Sheets с карточками из Seller API.
`/probs` перенаправляет на неё. Пробник и доставка для покупателя стоят 0 ₽,
эквайринг не вызывается. Один пробник на аккаунт обеспечивается уникальным
`Order.probeUserId` в PostgreSQL, включая параллельное оформление.

## Настройки

Docker Compose читает корневой `.env`. Для работы нужны:

- `OZON_CLIENT_ID`, `OZON_CLIENT_SECRET` — частное приложение Ozon Доставки.
- Доступы: `delivery-api.delivery`, `delivery-api.delivery-point`,
  `delivery-api.order`, `delivery-api.posting`.
- `OZON_DELIVERY_SHIPMENT_METHOD_ID=1020005036837360` — проверенный активный
  способ отгрузки «BAGINI — Москва, Складочная 1с5».
- `OZON_SELLER_CLIENT_ID`, `OZON_SELLER_API_KEY` — карточки товаров.
- `SHEET_URL`, `SHEET_SCRIPT_TOKEN` — остатки и атомарное резервирование пробников.
- Рабочие PostgreSQL и Redis.

Получатель должен быть зарегистрирован в Ozon с номером своего аккаунта магазина.
Перед оформлением сервер проверяет номер и доступность выбранного ПВЗ.
Доставку оплачивает отправитель с баланса Ozon Доставки. Посылку нужно физически
собрать и передать Ozon по настроенному способу отгрузки.

Габариты по умолчанию: 150 × 100 × 50 мм, 100 г, объявленная стоимость 100 ₽.
При необходимости задайте `PROBE_LENGTH_MM`, `PROBE_WIDTH_MM`, `PROBE_HEIGHT_MM`,
`PROBE_WEIGHT_G`, `PROBE_DECLARED_VALUE`. Объявленная стоимость — страховочная
оценка, покупателю она не начисляется.

В корневом `.env` на сервере используйте `PROBE_DECLARED_VALUE=100`.
В предварительном расчёте заказа №53 объявленная стоимость 1 ₽ приводила к
`delivery_calculation_error`, а 100 ₽ дала успешный расчёт: доставка 101 ₽,
страховка 10 ₽, срок 5 дней. Это предварительные расходы отправителя для
данного запроса; стоимость заказа покупателя остаётся 0 ₽. Минимальная
допустимая объявленная стоимость из этого сравнения не установлена.

## Применение изменений

Новая миграция обязательна: Ozon использует int64, и реальный ID способа отгрузки
не помещается в PostgreSQL INTEGER. Миграция также добавляет сохранённый запрос
для безопасного восстановления после таймаута.

Из корня проекта на сервере:

```sh
docker compose build backend frontend
docker compose run --rm --no-deps backend npx prisma migrate deploy
docker compose up -d backend frontend
docker compose logs --tail=100 backend
```

После запуска сервер в фоне загружает справочник ПВЗ. Первое наполнение может
занять несколько минут. Сообщение «Пункты выдачи Ozon обновлены» означает, что
обход завершён; затем справочник обновляется раз в сутки. При ошибке неполный
обход не помечается завершённым, а прежние ПВЗ не закрываются.
Если Ozon перечислил удалённые ПВЗ в ответе `delivery-point/info` с HTTP 404,
сервер пропускает только эти ID и повторяет запрос для остальных. Такие пункты
закрываются в локальном справочнике после успешного завершения обхода.

При локальном запуске Nest не загружает корневой `.env` автоматически.
Передайте переменные окружения процессу, например из каталога backend:
`node --env-file=../.env dist/src/main.js`.
Адреса `postgres` и `redis` в корневом `.env` предназначены для Docker-сети.

## Выбор ПВЗ на карте

В корзине пробника открывается окно с картой и списком адресов. Используются
готовые React Leaflet, Leaflet и react-leaflet-cluster; подложка по умолчанию —
OpenStreetMap, отдельный API-ключ не требуется. Геолокация запрашивается только
по нажатию «Рядом со мной». Выбор сохраняется после подтверждения; закрытие окна
не меняет адрес заказа. На телефоне окно занимает весь экран.

Поиск `/delivery/points?q=...` возвращает координаты вместе с адресами.
`/delivery/points/map?south=...&north=...&west=...&east=...` отдаёт до 250 пунктов
в видимой области карты и признак `truncated`, если нужно увеличить масштаб.
Оба метода требуют авторизацию и выбирают из локального справочника только
активные пункты, совместимые с настроенным способом отгрузки. Доступность
конкретной посылки дополнительно проверяется перед оформлением, как и раньше.

Карта подгружается только при открытии окна выбора. Если подложка недоступна,
можно выбрать ПВЗ через поиск и список. Стандартные тайлы OpenStreetMap имеют
ограничения доступности и нагрузки. Чтобы подключить своего провайдера тайлов,
задайте `NEXT_PUBLIC_MAP_TILE_URL` (с шаблоном `{z}/{x}/{y}`) и его HTML-атрибуцию
в `NEXT_PUBLIC_MAP_ATTRIBUTION` в `frontend/.env` перед сборкой фронтенда.
Атрибуция OpenStreetMap видна в стандартной конфигурации карты.

Для карты нужно обновить и пересобрать оба приложения; новая миграция базы
для этой функции не требуется — координаты уже хранятся в справочнике:

```sh
docker compose up -d --build --no-deps backend frontend
```

## Статусы и сбои

Перед резервированием пробника вызывается `order/checkout` с получателем,
выбранным ПВЗ, габаритами и объявленной стоимостью. Это отдельный расчёт тарифа:
успех `delivery-point/check-availability` сам по себе не означает, что тариф
рассчитан. Плановое время отгрузки на сайте не задаётся, поэтому `cutoff_at`
не передаётся ни в `checkout`, ни в `create`: Ozon определяет текущее время
для каждого запроса. Время из ответа расчёта не копируется в создание заказа,
поскольку за время резервирования оно уже становится прошлым. Старые сохранённые
значения `cutoffAt` при повторной отправке игнорируются. Тариф отправителя не
включается в стоимость заказа покупателя.

`posting/approve` работает асинхронно: до подтверждения готовности к отгрузке
заказ остаётся `pending` и оплаты не требует. Статус обновляется при открытии
страницы заказа или страницы пробников. После таймаута создания повторяется
сохранённый запрос с прежним UUID, без второго списания остатка.

Если `posting/approve` возвращает `posting_not_found`, подтверждение того же
номера повторяется через 0,5, 1,5 и 3 секунды. Новый заказ в Ozon не создаётся.
Если ошибка сохраняется, заказ остаётся `pending`, а остаток и лимит аккаунта
сохраняются. При следующем открытии заказа сервер проверяет `posting/info`;
для статуса `created` подтверждение повторяется.

Это обработка неопределённого результата подтверждения, а не подтверждение
того, что причиной 404 всегда является задержка Ozon. Постоянную ошибку нужно
разбирать с поддержкой Ozon по номеру отправления и trace ID. В логах создания
теперь сохраняются `ext_id`, `order_number` и `posting_number`, без телефона
получателя. Номер отправления выбирается по `request_id` из ответа создания.
Заказ становится `confirmed` только после успешного статуса в `posting/info`.

При определённой ошибке оформления и успешной отмене отправления резерв и лимит
аккаунта освобождаются. Пока отмена не подтверждена, они сохраняются: это защищает
от второго пробника при уже существующем отправлении. Если резервирование в
Google Sheets либо запись результата резерва в БД прерваны, заказ и остаток
нужно сверить вручную; таблица и PostgreSQL не поддерживают общую транзакцию.

Проверки 13 ноября 2026: OAuth и все четыре доступа работают; собранный сервис
возвращает 9 бесплатных пробников; расчёт заказа — 0 ₽; список и сведения о ПВЗ
доступны; проверенный ПВЗ принимает посылку с указанными габаритами.
Реальные заказы и платные отправления при проверке не создавались.

### `delivery_calculation_error` при оформлении

Это отказ расчёта тарифа в Ozon. Он отличается от `NotEnoughBalance`, который
возникает при подтверждении отправления. Сам по себе успешный поиск ПВЗ не
исключает эту ошибку.

В ответе API теперь сохраняются `deliveryCode`, `deliveryOperation` и, если Ozon
прислал заголовок `x-o3-trace-id`, `traceId`. Эти данные также выводятся в логах.
При повторяющейся ошибке расчёта передайте поддержке Ozon Доставки код ошибки,
trace ID, время запроса, ID способа отгрузки и ПВЗ, габариты и объявленную стоимость.
Секрет приложения и токен доступа для этого не нужны.

Для предварительного расчёта по существующему заказу из корня проекта на сервере:

```sh
docker compose exec backend node scripts/diagnose-ozon-delivery.cjs 53
```

Скрипт читает получателя указанного заказа и передаёт его номер только в Ozon
для `order/checkout`; телефон не выводится. Он сравнивает текущие параметры,
гипотетические объявленные стоимости 1 ₽ и 100 ₽ и время отгрузки
через сутки. Настройки приложения не меняются, отправления и резервы не
создаются, деньги не списываются. Перед запуском должны быть собраны текущие
исходники backend; скрипт включается в его Docker-образ.
